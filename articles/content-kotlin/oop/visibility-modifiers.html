Kotlin Visibility Modifiers: public, private, protected, internal & File-Level Visibility

Kotlin visibility modifiers control where classes, functions, properties, constructors, and other declarations can be accessed. The four modifiers are public, private, protected, and internal.

Quick answer: Kotlin declarations are public by default. A top-level private declaration is visible only inside the same file, while internal is visible throughout the same module.

1. Visibility Modifiers at a Glance

ModifierTop-level declarationClass member
publicVisible everywhereVisible everywhere the containing type is visible
privateVisible only in the same fileVisible only inside the declaring class
protectedNot allowedVisible in the class and subclasses
internalVisible in the same moduleVisible in the same module

2. File-Level Visibility in Kotlin

File-level visibility applies to declarations written directly in a Kotlin file rather than inside a class. This is especially important for the private modifier.

// Analytics.kt
private const val TAG = "Analytics"

private fun normalizeEventName(name: String): String {
    return name.trim().lowercase()
}

fun trackEvent(name: String) {
    println("$TAG: ${normalizeEventName(name)}")
}

TAG and normalizeEventName() are available anywhere inside Analytics.kt, but code in another file cannot access them. The public trackEvent() function remains accessible to callers.

3. private at File Level vs Class Level

  • Top-level private: visible throughout the same Kotlin file.
  • Class-member private: visible only inside the declaring class.
private fun fileHelper() = Unit

class Example {
    private fun classHelper() = Unit
}

4. The internal Modifier

internal is useful when multiple files or packages inside one module need access to a declaration, but consumers of another module should not treat it as public API.

internal class SessionStore {
    internal fun clear() { /* module-only API */ }
}

A Kotlin module is a set of source files compiled together, such as a Gradle module. Package boundaries do not define internal visibility.

5. The protected Modifier

protected is only valid for class members. It makes a member available inside the declaring class and subclasses.

open class BaseRepository {
    protected fun logRequest() = println("request")
}

class UserRepository : BaseRepository() {
    fun load() {
        logRequest()
    }
}

6. Choosing the Right Visibility

  • Use private for implementation details that should not become dependencies.
  • Use internal for module-level APIs shared across files or packages.
  • Use protected only when subclasses genuinely need an extension point.
  • Keep public APIs intentional because callers can become coupled to them.

7. Common Interview Questions

  • What is the default visibility in Kotlin? public.
  • What does file-level private mean? The declaration is accessible only from the same Kotlin file.
  • Can a top-level declaration be protected? No.
  • What is the difference between private and internal? private is limited to a class or file; internal is visible across the same module.
  • Is internal the same as package-private in Java? No. Kotlin internal is module-scoped, not package-scoped.

9. Key Takeaways

  • Kotlin has four visibility modifiers: public, private, protected, and internal.

  • Prefer the narrowest visibility that satisfies the design.
