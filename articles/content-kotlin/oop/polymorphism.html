Polymorphism in Kotlin: Types, Examples, Overriding & Interfaces

Polymorphism in Kotlin means writing code against a common type while allowing different objects to provide their own behavior. In practice, Kotlin uses inheritance, interfaces, method overriding, and function overloading to let the same API work with multiple concrete types.

Quick answer: runtime polymorphism happens when a parent-class or interface reference points to different implementations and Kotlin dispatches the overridden function at runtime. Function overloading is commonly described as compile-time/static polymorphism.

1. Why Polymorphism Matters

  • Loose coupling: depend on a parent type or interface instead of one implementation.
  • Extensibility: add a new implementation without rewriting the code that consumes the common type.
  • Testability: interfaces make it easier to swap production implementations for fakes or test doubles.
  • Reuse: shared calling code can work with many implementations.

3. Compile-time Polymorphism with Function Overloading

The same function name can have multiple parameter lists. Kotlin chooses the matching overload from the arguments supplied by the caller.

class Calculator {
    fun add(a: Int, b: Int) = a + b
    fun add(a: Int, b: Int, c: Int) = a + b + c
}

fun main() {
    val calc = Calculator()
    println(calc.add(2, 3))       // 5
    println(calc.add(2, 3, 4))    // 9
}

4. Runtime Polymorphism with Method Overriding

Kotlin classes and members are final by default. Mark the parent class and overridable function with open, then use override in subclasses.

open class Animal {
    open fun sound() = println("Some sound")
}

class Dog : Animal() {
    override fun sound() = println("Bark")
}

class Cat : Animal() {
    override fun sound() = println("Meow")
}

fun main() {
    val animals: List<Animal> = listOf(Dog(), Cat())
    animals.forEach { it.sound() }
}

The list stores the common type Animal, but each call uses the implementation belonging to the real object. That is runtime polymorphism.

5. Polymorphism with Kotlin Interfaces

Interfaces are often the cleanest way to express polymorphic behavior because callers depend on a capability instead of a concrete class.

interface PaymentProcessor {
    fun pay(amount: Double)
}

class CardProcessor : PaymentProcessor {
    override fun pay(amount: Double) = println("Card payment: $amount")
}

class WalletProcessor : PaymentProcessor {
    override fun pay(amount: Double) = println("Wallet payment: $amount")
}

fun checkout(processor: PaymentProcessor, amount: Double) {
    processor.pay(amount)
}

6. Real Android Example

A common Android example is depending on an interface from a ViewModel or use case while providing different repository implementations for production, previews, or tests.

interface UserRepository {
    suspend fun loadUser(): User
}

class NetworkUserRepository : UserRepository {
    override suspend fun loadUser(): User = api.fetchUser()
}

class FakeUserRepository : UserRepository {
    override suspend fun loadUser(): User = User("Test")
}

The calling code only knows about UserRepository. The concrete behavior can change without changing the caller.

7. Polymorphism vs Inheritance vs Abstraction

  • Inheritance creates an is-a relationship between classes.
  • Polymorphism lets code use a common type while behavior varies by implementation.
  • Abstraction exposes the important contract while hiding unnecessary implementation detail.

8. Common Interview Questions

  • What is polymorphism in Kotlin? The ability to use objects through a common type while each object can provide different behavior.
  • How is runtime polymorphism achieved? Through overridden members and interface implementations.
  • Why are open and override required? Kotlin makes classes and members final by default to prevent accidental inheritance and overriding.
  • Can interfaces provide polymorphism? Yes. Multiple classes can implement one interface and be consumed through that interface type.

10. Key Takeaways

  • Program to a common type when implementations may change.
  • Use overriding and interfaces for runtime polymorphism.
  • Use overloading when multiple signatures for the same operation make the API clearer.
  • Prefer interfaces when you want flexible, testable application architecture.
