What Is Model Context Protocol (MCP)?

Updated for MCP 2026-07-28

Model Context Protocol, usually shortened to MCP, is an open protocol for connecting AI applications to external capabilities and context in a standardized way. Instead of teaching every model integration how to talk to every database, service, file system, or business API independently, MCP defines a common contract that AI hosts and external servers can use to discover and invoke capabilities.

A useful mental model is that MCP sits between an AI application and the systems the application wants to use. The model itself is not the protocol. The host application decides when MCP is available, a client speaks MCP, and an MCP server exposes things such as tools, resources, or prompts.

What problem does MCP solve?

Without a shared protocol, every integration tends to invent its own discovery format, schema conventions, authentication behavior, transport, and error handling. That works for one or two tools, but becomes expensive when an application must support dozens of data sources or when a server should work across multiple AI clients.

MCP standardizes the interaction boundary. A compatible host can connect to a compatible server and discover what the server offers without requiring a one-off integration for every pairing.

What can an MCP server expose?

At a high level, MCP servers can expose callable tools, readable resources, and reusable prompts. The protocol has also evolved to support richer interaction patterns and extensions. The 2026-07-28 release formalized extensions and moved the core protocol toward stateless request/response behavior, which makes it easier to scale ordinary HTTP deployments.

MCP is not an agent framework

This distinction matters. MCP does not decide how your agent reasons, when it should call a tool, how memory works, or whether you use one agent or many. Those responsibilities live in your agent runtime or application. MCP standardizes access to external capabilities.

Short version: an agent framework manages the agent loop; MCP standardizes how external capabilities are exposed to that loop.

A minimal architecture

Imagine a coding assistant that needs GitHub, PostgreSQL, and an internal deployment service. The host could connect to three MCP servers. Each server publishes a catalog of capabilities. The host can expose the relevant ones to the model and route tool calls back to the correct server.

This decoupling is the main architectural benefit: the GitHub server does not need to know which LLM you use, and the LLM-facing application does not need custom protocol logic for every integration.

When MCP is useful

  • You want one integration to work with multiple AI clients.
  • Your agent needs many external tools or data sources.
  • You want a clear boundary between AI orchestration and business systems.
  • You need standardized discovery and schemas rather than custom glue code.
  • You are building reusable internal or public AI integrations.

When MCP may be unnecessary

If one backend calls one internal function and there is no need for reuse, discovery, portability, or multiple clients, a normal function call or REST API may be simpler. MCP is most valuable when the integration boundary itself deserves standardization.
