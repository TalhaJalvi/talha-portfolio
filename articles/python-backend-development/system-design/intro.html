System Design Basics

System design is the discipline of turning product requirements into an architecture that can handle expected traffic, data, failures and future growth.

1. Start with requirements

Separate functional requirements from non-functional requirements. Functional requirements describe what the product must do. Non-functional requirements describe qualities such as latency, availability, durability, consistency, security and cost. A design for ten internal users is different from one for ten million public users, even when the feature list is identical.

2. Estimate the shape of the workload

You do not need perfect numbers. Estimate daily active users, requests per second, read/write ratio, average payload size, storage growth and traffic peaks. These estimates help you decide whether a single database is enough, whether caching is useful and where horizontal scaling may become necessary.

3. Define interfaces and data

Sketch the main API operations and the data entities they touch. Decide what must be strongly consistent and what can be eventually consistent. Choose storage based on access patterns rather than fashion: relational databases are excellent for transactions and relationships, while key-value, document, search and analytical stores solve different problems.

4. Draw the high-level architecture

A typical web system may include clients, a load balancer, stateless application servers, a primary database, caches, object storage and background workers. Introduce extra components only when a requirement justifies them. Every queue, cache and service adds operational complexity.

5. Identify bottlenecks and failure modes

Ask what happens when traffic doubles, the database becomes slow, a downstream API fails, a worker crashes or a region is unavailable. Reliability patterns include timeouts, retries with backoff, circuit breakers, replication, health checks, queues and idempotent operations.

6. Discuss trade-offs

Strong system design answers rarely claim one universal solution. Explain why you chose an approach, what it costs and when you would change it. For example, caching lowers latency and database load but introduces invalidation and staleness concerns. Sharding raises write capacity but complicates queries and rebalancing.

Interview rule: communicate your assumptions. The interviewer is usually evaluating your reasoning and prioritization more than a single diagram.

A repeatable order

  1. Clarify scope and requirements.
  2. Estimate traffic and storage.
  3. Define APIs and data model.
  4. Draw the simplest viable architecture.
  5. Deep-dive into the most important bottlenecks.
  6. Cover reliability, security and observability.
  7. Summarize trade-offs and future scaling.
