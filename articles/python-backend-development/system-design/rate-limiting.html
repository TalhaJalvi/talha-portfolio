Rate Limiting

Rate limiting protects a service from abuse, accidental traffic spikes and noisy clients by controlling how many operations are accepted in a period.

Where to enforce limits

Limits can live at an API gateway, reverse proxy, application layer or a combination. Gateway-level limits reject excessive traffic before it consumes expensive application resources. Application-level limits are useful when rules depend on business context such as a subscription plan, user identity or operation cost.

Common algorithms

Fixed window

Count requests in a fixed interval such as 100 requests per minute. It is simple, but traffic can burst around a window boundary.

Sliding window

Track activity over the most recent interval. This produces smoother limits but may require more state. Implementations often use timestamps or approximations based on adjacent fixed windows.

Token bucket

A bucket refills tokens at a steady rate. Each request consumes a token. This permits controlled bursts while maintaining a long-term rate and is widely useful for APIs.

Distributed systems

When many application instances serve the same user, counters must be coordinated. A shared low-latency store such as Redis is common. The update should be atomic so simultaneous requests cannot bypass the limit. For very large systems, exact global limits may be traded for lower coordination cost and approximate local quotas.

Good API behavior

Return HTTP 429 when a client exceeds an HTTP API limit. Provide enough information for well-behaved clients to retry later, often through a Retry-After header or documented reset metadata. Clients should use backoff instead of retrying aggressively.

Choose the right key

You can limit by user ID, API key, IP address, tenant, route or a compound key. IP-only limits can punish many legitimate users behind one network, while user-only limits may not help before authentication. Production systems frequently combine several layers.

Design trade-off: rate limiting is partly a fairness policy. Decide whose resources you are protecting and what kind of burst behavior the product should permit.
