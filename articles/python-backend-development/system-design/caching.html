Caching Strategies

Caching trades freshness and complexity for lower latency, fewer expensive computations and reduced load on databases or external services.

Cache-aside

The application checks the cache first. On a miss it reads from the source of truth, stores the result with a TTL and returns it. This pattern is simple and gives the application control, which is why it is common with Redis.

Read-through and write patterns

In read-through caching, the cache layer is responsible for loading missing data. Write-through updates the cache and backing store together. Write-behind accepts a cache update and persists it asynchronously, improving write latency but increasing durability and ordering concerns.

Invalidation is the hard part

When underlying data changes, cached copies can become stale. Strategies include short TTLs, explicit invalidation after writes, versioned keys and event-driven invalidation. The acceptable staleness depends on the domain: a profile image can tolerate more delay than an account balance.

Cache key design

Keys should include every input that changes the result, such as tenant, locale, permissions or query parameters. Missing dimensions can leak one user's result to another or return logically incorrect data.

Cache stampedes

If a popular key expires, many requests may simultaneously recompute it and overload the source. Mitigations include request coalescing, distributed locks, stale-while-revalidate behavior and adding jitter to expiration times.

What not to cache

Do not cache merely because Redis is available. Highly volatile data, security-sensitive personalized responses and cheap infrequently requested operations may gain little. Always define the source of truth and the consistency expectation.

Measure first: track cache hit ratio, latency, eviction rate and source load. A cache that misses constantly adds another network hop without solving the bottleneck.
