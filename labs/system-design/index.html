Simulation assumptions & limitations

This lab is an educational capacity model, not a benchmark. An API instance is assumed to sustain 10,000 requests/second for this specific scenario. The cache lookup is assumed to be fast when healthy; database demand is modeled from cache misses plus writes. Latency increases as utilization approaches or exceeds component capacity.

Real systems depend on hardware, code paths, query complexity, network topology, connection pools, payload sizes and many other factors. The point of the lab is to practice reasoning from stated assumptions rather than memorize universal capacity numbers.

What to learn

Capacity is a chain, not a single number.

A load balancer does not save an under-provisioned application tier. More API servers do not help if every request overwhelms the database. A cache helps only when its hit rate and failure behavior are understood.

1Start with demand. Convert the workload into requests each component actually sees.
2Find the narrowest capacity. The first saturated dependency sets effective throughput.
3Test failures. A healthy design should account for what happens when an optimization disappears.
